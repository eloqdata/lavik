# Measurement definitions and limits

## Machine and isolation

The original host has eight logical CPUs, approximately 62 GiB memory, Intel Xeon Platinum 8573C processors, Linux 6.17.0-1018-azure, and local NVMe exposed as `/dev/md127`, ext 4 mounted at `/mnt/local_nvme` with `rw,relatime,stripe=384`. The machine topology, mount and device descriptions are retained in `evidence/host.json`. Source, target, capture and clients share this host and storage. Builds and heavy tests were stopped during measurement; unrelated light host services remained, so these are not measurements from a completely isolated OS.

Data-worker layouts are 1→1 (source CPU 0, target CPU 1, client/capture CPUs 6–7) and 4→2 (source CPUs 0–3, target CPUs 4–5, client/capture CPUs 6–7). The runtime also has a control worker sharing each process's assigned CPU set. `--no-pin-workers` lets the OS schedule workers within those disjoint process CPU sets. Comparing different worker layouts changes both source flow count and target parallelism; only compare variants within one case for a controlled optimization estimate.

Each run owns a new network namespace and veth pair. Added RTT is split equally between the two dedicated egress netem qdiscs; both use explicit `limit100000`. An added RTT of 0 ms means no injected delay on this virtual path, not literally zero observed network latency. Twenty idle application PING observations before seeding provide the recorded RTT check; PING includes application scheduling and is not an ICMP or unloaded hardware-only link measurement. Existing host-wide qdiscs are not changed. Foreground writes use source loopback and do not traverse the injected replication RTT.

The common server configuration is a 2 GiB data file and 2 GiB max memory per process,64 MiB replication backlog globally per process (64 MiB per source flow with one worker,16 MiB per source flow with four workers),100 ms flush interval, and 64 MiB registered buffers per worker. Publisher queues are 16 MiB per worker except in explicitly named `queue32` mixed-live cohorts, which use32 MiB per worker. These queue quotas are configured by `--replication-publish-queue-mb-per-worker`; the backlog uses the process-global `--repl-backlog-size` setting and is divided across data-worker flows. A two-worker target consequently has32 MiB backlog capacity per flow under the same64 MiB process setting. These publisher-queue quotas are distinct from the implementation's sender credit window. Every run starts fresh source/target data directories; seed/startup are outside the FULL timer. Source data was just seeded; no cold-cache or cache-eviction preparation was performed. Fresh data directories do not make this a cold-cache benchmark. The 8/128 MiB corpora do not establish performance for datasets larger than memory or for disk-limited recovery. No storage I/O or durability subphase was separately instrumented.

## Corpora and live writes

- Large strings: eight keys,16 MiB each,128 MiB value payload.
- Large hashes: four keys,32,768 fields per key,1,024-byte values;128 MiB values plus field names/encoding overhead. Seeding uses deterministic RDB RESTORE payloads.
- Dense ordinary records:32,768 keys with 4,096-byte values,128 MiB; one selected hot partition per source worker. This deliberately provides multiple record frames per partition+DB.
- Sparse/uniform ordinary records:2,048 keys with 4,096-byte values,8 MiB. The smaller corpus bounds the per-partition stop-and-wait duration. It must not be compared as an absolute throughput counterpart to the 128 MiB dense corpus.
- All formal data is in DB 0. Functional coverage in other DBs is separate from these performance measurements.

The mixed large writer rotates existing large keys, with one `MULTI; SET; EXEC` transaction per second and five seconds of warmup. The ordinary writer performs small SETs over up to 1,024 separate keys at a requested 500 ops/s, also with five seconds of warmup. Each uses one synchronous rate-limited client; after a blocked request it does not accumulate a burst of missed arrivals. This is a controlled live-load measurement, not a saturated open-loop service-capacity test. FULL duration changes the number of successful live writes and transmitted bytes, which are retained for every run.

## End-to-end FULL time

The timer starts immediately before `LAVIK.REPLICAOF` and ends when the target's polled `INFO replication` reports ONLINE. It includes admission/preflight, reset, scan/transfer, handoffs, final cut and detection delay. Polling sleeps 20 ms between probes, and the target INFO requests also cross the injected link. It excludes initial seeding, server startup, and the complete digest check afterward. It does not imply that every background physical-space reclamation or durability action has finished.

After FULL, the writer is stopped and joined. A post-FULL sentinel is written for each source flow and awaited on the target. Then the runner checks complete source/target content digests and database key counts. A final equal digest alone cannot make a retried FULL into a valid single-attempt performance sample: the external guard additionally requires one source session and each expected flow selected=FULL exactly once.

Every comparison retains three repetitions with pair order A/B, B/A, A/B. Tables show all three values in repetition order and the median. Time reduction is `100*(1 - after_median/before_median)`; negative numbers mean slower. Speedup is `before_median/after_median`. Paired ratios are separately available in comparison JSON. With three repetitions and visible variation, neither a median nor a min–max plot is a statistical-confidence claim. No slow-but-valid run was removed as an outlier.

## Frame distribution and optional byte spans

The source-only native-output capture uses tcpdump immediate mode, packet-buffered output, a 16 MiB capture buffer, and the client CPU set. The capture starts before FULL and stops after the writer joins plus a200ms drain, before the post-FULL sentinel writes. Its complete-frame counts can include a brief post-ONLINE stream tail and are not a strict `[FULL start, FULL end)` packet window. Captured runs require zero kernel capture drops, all expected native flows, one CUT per flow, and no unresolved TCP gap or unparsed native tail. **Zero capture drops do not prove zero network/qdisc loss.** Original runs do not generally include qdisc counter snapshots; both-end counters were saved only during the stalled-run diagnosis. The separate offline TCP-overlap analyzer reports repeated source TCP payload observations, consistent with retransmission, not a qdisc drop rate or a receiver-ACK loss measure.

The tools’ `wire_bytes` fields count reconstructed native frame payload plus its 16-byte frame header after TCP deduplication. They exclude TCP/IP/Ethernet headers, retransmission bytes, and reverse ACK traffic; they are not total physical-link traffic. Per-run frame count, native frame bytes, record kinds and full partition+DB maps are retained in compact raw results. In dense data, many frames share a partition+DB and can use the new ordinary-record window. Sparse groups with only one frame cannot fill that window before the conservative partition/DB barrier. A dense hot-partition result is therefore not evidence of broad sparse/uniform speedup.

`frame-spans.json` is an offline observation of the first selected record byte through the last selected record byte at the source veth. The span includes intervening scanning, I/O, ACK waits, scheduling, idle time and other frame kinds. It is neither an exclusive snapshot phase nor pure sending time. Reset, record and handoff spans overlap and interleave; do not add them, subtract them from FULL as a stage decomposition, or treat a single-packet zero span as zero completion latency. The timestamp helper rejects reordered/gapped captures when timing is ambiguous, independently of whether the normal parser eventually reconstructed the complete stream.

Repeated ValueBegin keys in a live capture establish repeated large-object transmission. The wire format does not carry a baseline/override/FIFO origin label, so those observations cannot support separate per-origin speedup figures. Process correctness gates cover origin behavior independently; see the validation evidence linked from the report.

The uncaptured controls match selected primary cases but run in a later cohort. They examine observation sensitivity without proving a precise causal overhead subtraction. Full pcap output competes for the same storage and consumes CPU. Report captured and uncaptured cohorts separately and preserve any change of direction.

## CPU, memory and foreground latency

Sampling starts before warmup and nominally repeats every 0.5 s. The report's FULL-only resource summaries filter rows by collection-start timestamp inside `[FULL start, FULL end)`. Actual sample intervals vary because metrics are read serially; node collection times are approximate. `result.metric_peaks` covers the wider warmup/FULL/post-FULL sampling interval, so it is not the same quantity as a FULL-only sampled peak.

RSS peaks are maxima over observed samples, not exact allocation high-water marks. Worker metrics are summed within a row and then peaked, rather than summing independent worker maxima. Retained-memory/FULL reserved/queue gauges do not directly measure exact sender-window retained-credit peaks, and short transfers can hide transients between samples.

CPU comes from process tick differences divided by the recorded clock-tick rate and the valid sample interval wholly inside FULL. Per-run JSON retains interval start/end, duration, fraction of FULL, valid sample count, sampled CPU seconds, and mean busy cores; CSV carries the selected summary fields. Resource tables report the median of the three per-run sampled RSS peaks and the median of per-run mean busy cores, not a cohort-wide RSS maximum or a whole-FULL CPU estimate. There is no extrapolation to total FULL CPU cost when sampling covers only part of the transfer; fewer than two valid samples yields no CPU estimate. Disk I/O, target apply time, exact per-frame ACK latency, and exclusive scan time were not measured.

Foreground latency includes every successful operation **begun** during FULL, including ones completed after FULL ends. The writer is joined before summarizing. Completed QPS instead counts successful operations whose **completion** falls inside FULL, possibly including a warmup-started request; the populations need not have the same count. Failures and crossed-end requests are recorded separately. Raw attempts are retained on NVMe. Low-rate large transactions provide too few samples for reliable p 99/p 99.9 conclusions: inspect count, median/max and all raw values. Even the ordinary writer is one controlled client, so its latency cannot establish whole-service tail behavior at arbitrary concurrency.

## Acceptance, exclusions and cleanup

Accepted evidence requires all-flow ONLINE, one FULL attempt per flow, verified equal complete digests and key counts, post-FULL fences, no writer error, no cleanup error, and complete capture if enabled. A failed instrumentation check before digest leaves the dataset unverified; it is neither a proven replication failure nor a successful digest comparison.

The original 16 MiB-queue large-live 20 ms baseline was explicitly aborted after a prolonged no-progress state. It is not a 900 s timeout value or a speedup denominator. A distinct 32 MiB-queue matched cohort tests the same live workload with publisher-fence headroom; it is a configuration workaround, not a production deadlock fix. The original dense four-flow 20 ms cohort had a kernel capture drop; its two accepted partial observations and invalid run remain separate from its complete replacement cohort.

Only successful task-owned source/target `data` files are deleted after process shutdown and verification. Failed data remains. Result/acceptance/driver outcome, server logs, pcap and raw samples remain on NVMe. Reviewable compact originals, sampled summaries, conditions, hashes, recipes and analysis tools are bundled with the reports. Original measurement artifacts and the exact source/binary provenance must be distinguished from later documentation commits on the PR branches.
